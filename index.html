Bloomery

A build system configured entirely in TOML. No embedded scripting language: conditionals are dispatch tables, file lists are reserved-key tables, everything else is {name} interpolation.

source · docs · github.com/bloomery-build

Install

pip install bloomery-build

Package name is bloomery-build (bloomery was taken); the command is bloomery. Python 3.8+. python -m bloomery works uninstalled. 

bloomery install     # pip install -e a git checkout (clones one if needed)
bloomery update      # git pull that checkout, or pip upgrade if not a checkout
bloomery uninstall
bloomery init         # write a starter bloomery.toml

A manifest

[meta]
name = "myproject"
system = "c++"                             # bundled mold to load

[variables]
compiler = "g++"
debug_flags = { on = "debug", true = "-g -O0", false = "-O2" }

[tasks.build]
command = "{compiler}"
flags = "-std=c++17 {debug_flags}"
files = { ending = [".cpp", ".cc", ".cxx", ".c"] }
output = "-o {output}"

[tasks.run]
depends = ["build"]
command = "{output}"
bloomery                    # build and run the default targets
bloomery --clean            # ignore the cache, rebuild everything
bloomery -D debug=false     # override a variable
bloomery -j4                # run independent tasks in parallel
bloomery --list             # list targets

A dispatch table (the { on = ... } form above) has to be the entire value of a field. It can't sit inside a longer string. -D and [profiles.X] both work by changing the variable a dispatch reads; there's nothing special-cased about the mechanism itself.

Molds

A mold is a compiler-default template, looked up by meta.system: project directory, then meta.mold_path, then $BLOOMERY_MOLD_PATH, then ~/.bloomery/molds/, then bundled (c, c++, rust, python). Earlier entries win, so a downloaded mold shadows the bundled one. 

bloomery mold get c++      # writes into ~/.bloomery/molds/, shadowing the bundled c++

Reach a mold's fields with {mold.field}; they aren't copied into the project's own variable namespace, so a mold field named files won't shadow a project variable of the same name.

Charges and alloys

External packages, handled outside the task graph since they resolve by package name instead of content hash. A charge is fetch/build instructions for one package; an alloy is the package-manager routing for one language (pip, npm, cargo, or the universal source alloy for anything with no manager). 

bloomery charge install c/zlib python:requests

c/zlib resolves a real charge file (source fetch + build); python:requests is ad-hoc: no charge file, straight through pip. Mix both in one call. Opt into running this automatically before a build:

[charges]
auto_install = true
use = ["c/zlib", "python:requests"]

Results land in .bloomery/vendor/<name>/; a task references them like any other path, e.g. -I.bloomery/vendor/zlib/include.

Registries

Contribution targets, one repo per kind of file:

  • MoldRegistry: compiler defaults per language
  • ChargeRegistry: <language>/<name>.toml per package
  • AlloyRegistry: package-manager routing beyond pip/npm/cargo/source
